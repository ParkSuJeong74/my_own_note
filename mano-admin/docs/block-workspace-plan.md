# Mano 블록 워크스페이스 전환 계획

브랜드의 기원과 장기 제품 범위는 [Mano 브랜드와 제품 비전](brand-product-vision.md)을
상위 기준으로 삼는다. 이 문서는 그 비전을 기존 Mano에서 안전하게 구현하는 전환 계획이다.

## 1. 문서 목적

Mano를 기능별 관리 화면의 모음에서, 매일 자연스럽게 열어 기록하고 정리하는 개인용
블록 워크스페이스로 확장한다. 기존 기능과 데이터는 유지하고 새 워크스페이스를 병행
구축한 뒤, 실제 사용성이 확인된 기능만 단계적으로 연결하거나 대체한다.

이 문서는 제품 목표, 사용자 경험, 데이터 모델, 기존 기능 연결 방식, 구현 순서,
전환 기준과 검증 방법을 정의한다. 특정 화면의 세부 디자인이나 구현 라이브러리는
각 단계 착수 시 별도 설계 문서에서 확정한다.

## 2. 배경과 문제

현재 Mano는 Todo, Calendar, Notes, Workspace, T1, 블로그, 자동화, 서비스 상태처럼
필요한 기능을 각각 제공한다. 그러나 기능별 페이지로 이동해 정해진 양식에 입력해야
하므로 다음 문제가 있다.

- 생각이 생긴 순간 바로 기록하기보다 적절한 메뉴와 입력 형식을 먼저 골라야 한다.
- 메모, 할 일, 일정과 외부 데이터가 서로 다른 화면에 있어 하나의 맥락으로 보기 어렵다.
- 새 기능을 추가할수록 메뉴와 전용 화면이 늘고 일상적인 진입 비용이 커진다.
- 기능은 존재하지만 사용자가 먼저 Mano를 열어야 할 이유가 약하다.
- 개인적인 작업 방식이 바뀔 때마다 전용 화면과 스키마를 수정해야 한다.

핵심 문제는 기능 부족이 아니라, 기록과 실행을 시작하는 기본 단위가 사용자의 생각보다
서비스 메뉴에 맞춰져 있다는 점이다.

## 3. 제품 결정

최종적으로 Mano의 기능별 고정 페이지를 제거하고, 사용자가 블록·데이터베이스·뷰·버튼을
조합해 필요한 페이지를 직접 만드는 하나의 워크스페이스로 전환한다. 전환 중에는 기존
화면을 유지하지만 이는 영구 구조가 아니라 기능 누락과 데이터 손실을 막는 안전망이다.

1. 페이지가 기본 진입점이다.
2. 페이지는 순서가 있는 블록으로 구성한다.
3. 데이터베이스, 뷰, 필터, 정렬과 액션 버튼도 페이지 안에서 사용자가 구성한다.
4. T1·블로그·일정·자동화 같은 수집기는 데이터만 공급하고 화면 구조를 강제하지 않는다.
5. 기존 전용 화면은 같은 기능을 새 페이지에서 만들 수 있을 때까지만 유지한다.
6. 기존 기능의 데이터와 동작을 빠짐없이 대체한 뒤 전용 라우트를 단계적으로 제거한다.
7. 고급 기능은 존재하되 기본 작성 화면과 설정 흐름은 설명 없이 쓸 만큼 단순해야 한다.

제품 정의는 **“내가 직접 구성하지만 관리 부담 없이 매일 쓰는 개인 운영 노트”**다.
다중 사용자 협업이나 Notion 파일 형식 호환은 목표가 아니지만, 개인 사용에 필요한
페이지·데이터베이스·뷰·자동화 구성 능력은 최종 제품 범위에 포함한다.

### 최종 상태

- 기본 애플리케이션 화면은 페이지 탐색, 검색, 설정과 휴지통뿐이다.
- Todo, Calendar, T1, 블로그, Workspace, 자동화와 상태 대시보드는 고정 메뉴가 아니다.
- 사용자는 빈 페이지에서 데이터 소스와 뷰를 추가해 이 화면들을 직접 구성한다.
- 처음부터 만들기 어렵지 않도록 선택 가능한 템플릿을 제공하되 템플릿 결과는 일반
  페이지와 블록이므로 사용자가 자유롭게 수정·삭제할 수 있다.
- 수집 scheduler, 알림, 인증, provider 연동은 백엔드 기능으로 유지한다. UI만 페이지
  구성 체계로 통합한다.

## 4. 목표와 성공 기준

### 목표

- 빈 페이지에서 3초 이내에 기록을 시작할 수 있다.
- 메모, 체크리스트, 일정과 기존 Mano 정보를 한 페이지 안에 배치할 수 있다.
- 페이지와 블록을 사용자가 원하는 구조로 재배열할 수 있다.
- 입력 내용은 별도 저장 버튼 없이 안전하게 저장된다.
- 기존 Mano 기능을 중단하지 않고 점진적으로 대체한다.
- 코드 수정 없이 기존 Mano 수준의 화면과 작업 흐름을 페이지 안에서 재구성할 수 있다.
- 모바일에서도 읽기, 빠른 기록과 체크 처리가 가능하다.

### 초기 성공 기준

- 새 홈을 최소 2주 동안 실제로 사용하고 주 5일 이상 방문한다.
- 일상적인 메모와 할 일의 과반을 새 워크스페이스에서 생성한다.
- 기록 생성부터 저장 확인까지 별도 전용 화면 이동이 필요하지 않다.
- 자동 저장 실패가 사용자에게 숨겨지지 않고 재시도할 수 있다.
- 기존 Notes, Todo, Calendar 데이터에 손실이나 의도하지 않은 중복이 없다.

성공 여부는 기능 개수가 아니라 반복 사용과 기록 시작 비용으로 판단한다.

## 5. 정보 구조

### 기본 화면

- 좌측 탐색: 홈, 검색, 즐겨찾기, 최근 페이지, 페이지 트리, 기존 Mano 메뉴
- 중앙 편집 영역: 페이지 제목, 속성, 블록 목록
- 보조 영역: 목차, 연결된 항목, 페이지 정보 또는 블록 설정
- 빠른 생성: 새 페이지, 빠른 메모, 오늘 할 일

모바일에서는 좌측 탐색을 서랍으로 전환하고 중앙 편집 영역을 우선한다. 보조 영역은
별도 시트로 연다.

### 페이지 계층

- 페이지는 최상위 또는 다른 페이지의 하위 페이지가 될 수 있다.
- 한 페이지는 부모를 하나만 가진다.
- 동일 부모 아래에서 사용자가 정한 순서를 유지한다.
- 삭제는 즉시 영구 삭제하지 않고 휴지통 상태로 전환한다.
- 즐겨찾기와 최근 방문은 계층과 별도로 관리한다.
- 순환 부모 관계와 자기 자신의 하위 이동은 허용하지 않는다.

## 6. 블록 모델

모든 블록은 공통으로 `id`, `pageId`, `type`, `position`, `content`, `createdAt`,
`updatedAt`을 가진다. 블록별 내용은 검증 가능한 JSON 구조로 저장한다.

### MVP 블록

| 블록 | 핵심 내용 | 주요 동작 |
| --- | --- | --- |
| Paragraph | 일반 텍스트와 인라인 서식 | 입력, 줄바꿈, 링크 |
| Heading | 1~3단계 제목 | 목차 생성, 접기 후보 |
| Bulleted list | 글머리 목록 | 들여쓰기, 순서 변경 |
| Numbered list | 번호 목록 | 들여쓰기, 번호 계산 |
| Todo | 내용과 완료 여부 | 체크, 미완료 필터 |
| Divider | 구분선 | 삽입, 삭제 |
| Callout | 강조 문구와 색상 | 메모·경고 표현 |
| Child page | 하위 페이지 링크 | 생성, 이동, 열기 |

### 다음 단계 블록

- 표 또는 데이터베이스 뷰
- 이미지와 파일 첨부
- 코드 블록
- 북마크
- T1 경기 뷰
- 블로그 미답글 뷰
- 캘린더 뷰
- 서비스 상태와 자동화 실행 상태 뷰

연결형 블록은 외부 데이터를 블록 내용에 복제하지 않는다. 대상 유형, 대상 ID, 표시
옵션만 저장하고 렌더링 시 최신 데이터를 읽는다.

## 7. 핵심 편집 경험

### 입력과 블록 생성

- 페이지를 열면 제목 또는 마지막 편집 위치에 바로 입력할 수 있다.
- `Enter`는 같은 종류의 다음 블록을 만든다.
- 빈 블록에서 `Backspace`는 앞 블록과 병합하거나 블록 종류를 초기화한다.
- `/` 명령으로 블록 종류를 검색하고 선택한다.
- Markdown 단축 입력(`# `, `- `, `[] ` 등)은 선택 기능으로 제공한다.

### 선택과 재배열

- 키보드로 블록 사이를 자연스럽게 이동한다.
- 하나 이상의 블록을 선택해 이동, 복제 또는 삭제할 수 있다.
- 드래그 핸들로 순서를 변경한다.
- 블록 이동 중 저장 충돌이 나면 임의로 덮어쓰지 않는다.

### 자동 저장

- 입력은 짧은 debounce 후 저장한다.
- 화면에는 `저장 중`, `저장됨`, `오프라인`, `저장 실패` 상태를 표시한다.
- 실패한 변경은 로컬에 유지하고 재시도할 수 있게 한다.
- 서버 버전이 달라진 경우 마지막 쓰기 승리로 조용히 덮지 않고 충돌을 알린다.
- 페이지 이동과 탭 종료 전에 미전송 변경을 최대한 전송한다.

초기 버전은 실시간 공동 편집을 지원하지 않는다. 동일 사용자가 여러 탭에서 편집하는
상황은 버전 번호를 이용한 낙관적 잠금으로 보호한다.

## 8. 검색과 탐색

- 페이지 제목과 텍스트 블록 내용을 통합 검색한다.
- 최근 열어본 페이지와 즐겨찾기를 빠르게 표시한다.
- 검색 결과에서 일치 문맥과 상위 페이지 경로를 보여준다.
- 휴지통 항목은 기본 검색에서 제외한다.
- 초기 검색은 PostgreSQL 전문 검색으로 구현하고 데이터 규모가 커질 때만 별도 검색
  시스템을 검토한다.

백링크, 태그, 전체 그래프 탐색은 MVP 이후 후보이며 기본 기록 경험보다 먼저 만들지
않는다.

## 9. 데이터 모델 초안

### pages

- `id`: UUID
- `parent_id`: nullable UUID
- `title`: text
- `icon`: nullable text
- `cover`: nullable text 또는 JSON
- `position`: 같은 부모 안의 정렬 키
- `is_favorite`: boolean
- `version`: 낙관적 잠금용 integer
- `archived_at`: nullable timestamp
- `created_at`, `updated_at`, `last_opened_at`

### blocks

- `id`: UUID
- `page_id`: UUID
- `parent_block_id`: nullable UUID
- `type`: 제한된 block type
- `position`: 같은 부모 안의 정렬 키
- `content`: JSONB
- `version`: 낙관적 잠금용 integer
- `archived_at`: nullable timestamp
- `created_at`, `updated_at`

### page_history

- 변경 주체, 대상 페이지, 변경 종류, 이전·이후 버전과 변경 시각
- 초기에는 전체 스냅샷보다 복구에 필요한 제한된 변경 기록을 우선한다.
- 보존 기간과 복구 UI는 구현 단계에서 저장 용량을 확인해 확정한다.

### linked_views

연결형 블록을 별도 테이블로 둘지는 구현 시 결정한다. MVP에서는 블록 `content`에
`sourceType`, `viewType`, `filter`, `sort`, `display`만 저장할 수 있다. 사용자 데이터
필터는 서버에서 허용 목록으로 검증하며 임의 SQL을 저장하지 않는다.

## 10. API 경계 초안

구체적인 URL과 payload는 구현 직전 확정하되 다음 책임을 분리한다.

- 페이지 목록·생성·수정·이동·보관·복구
- 블록 목록·생성·수정·이동·보관
- 여러 블록의 순서 변경을 하나의 트랜잭션으로 처리하는 batch API
- 페이지·블록 통합 검색
- 연결된 기존 Mano 데이터의 읽기 전용 조회
- 충돌 확인을 위한 `version` 또는 ETag

쓰기 API는 인증된 단일 사용자만 접근하더라도 입력 검증, 대상 소유 범위 확인,
요청 크기 제한과 트랜잭션을 적용한다. 블록 순서는 부동소수점 증가만 계속 사용하는
방식보다 충돌 없이 재정렬할 수 있는 정렬 키 또는 제한적인 재번호 부여를 사용한다.

## 11. 기존 Mano 기능 대체 계획

| 기존 기능 | 전환 중 | 제거 조건 |
| --- | --- | --- |
| Notes | 페이지 가져오기와 원본 병행 | 본문·태그·고정·검색·수정 이관 검증 |
| Todo | Todo 블록과 데이터베이스 뷰 병행 | 생성·완료·분류·일/월 필터를 사용자가 재구성 가능 |
| Calendar | 날짜 속성의 캘린더 뷰 병행 | 일정 CRUD·반복·Google 동기화 상태 처리 가능 |
| Workspace | 페이지 트리와 관련 데이터 뷰 병행 | Task·링크·설명·메모를 페이지에서 구성 가능 |
| Sticky note | Callout 또는 카드 뷰 제공 | 색상·정렬·접기·분류를 페이지에서 구성 가능 |
| 블로그 댓글 | 블로그 데이터 소스와 저장된 뷰 제공 | 수집·오래된 순·블로거 묶음·완료 처리가 모두 가능 |
| T1 | T1 데이터 소스와 경기 뷰 제공 | 일정·라이브·세트·밴픽·POM·수동 보정을 모두 표현 가능 |
| 자동화 | 실행 데이터 소스와 액션 버튼 제공 | 생성·승인·재시도·상태·오류 확인을 모두 수행 가능 |
| 서비스 모니터링 | 상태 데이터 소스와 카드 뷰 제공 | 상태·지표·외부 상세 링크를 대시보드로 구성 가능 |

기존 기능 라우트는 표의 제거 조건을 자동·수동 테스트로 충족하고, 데이터 이관 미리보기와
롤백 수단을 제공한 뒤에만 제거한다. 데이터 소스가 원본 테이블을 그대로 사용할 수 있으면
복제하지 않으며, 통합 모델로 옮길 때는 중복 방지와 취소 가능한 migration을 제공한다.

### 사용자가 직접 화면을 만드는 데 필요한 구성 요소

- 데이터베이스 생성, 속성 추가·수정·숨김과 행을 페이지로 열기
- Table, Board, List, Calendar, Gallery와 간단한 Timeline 뷰
- 뷰별 필터, 다중 정렬, 그룹, 표시 속성과 저장된 뷰
- 텍스트, 숫자, 선택, 다중 선택, 날짜, 체크박스, URL, 관계와 계산 속성
- 현재 페이지나 데이터 행을 대상으로 하는 생성·수정·완료·외부 링크 액션 버튼
- T1, 블로그, 일정, 자동화, 서비스 상태를 선택 가능한 읽기/쓰기 데이터 소스
- 페이지 템플릿, 데이터베이스 행 템플릿과 반복 가능한 기본 구성
- 모바일에서 설정은 단순화하되 조회·추가·완료 등 핵심 동작은 동일하게 제공

고급 설정은 단계적으로 펼치는 UI를 사용한다. 빈 페이지의 기본 상태에는 제목과 입력 영역만
보이고, `/` 메뉴에서 필요한 기능을 검색해 추가할 수 있어야 한다.

## 12. 단계별 구현 계획

### Phase 0 — 사용 흐름 검증

- 대표 사용 시나리오 5개 작성
- 데스크톱·모바일 정보 구조와 편집 흐름 와이어프레임
- 블록 저장 방식과 에디터 기술 검증용 작은 프로토타입
- 기존 데이터에 쓰지 않는 별도 스키마 확정

완료 기준: 빈 페이지 작성, 블록 생성·삭제·이동과 자동 저장 흐름을 시연하고 데이터
모델의 치명적인 제약이 없다.

### Phase 1 — 매일 쓰는 페이지 MVP

- 페이지 트리, 최근 페이지, 즐겨찾기
- Paragraph, Heading, 목록, Todo, Divider, Callout, Child page
- `/` 명령, 키보드 이동, 기본 드래그 정렬
- 자동 저장 상태, 충돌 방지, 휴지통
- 제목·본문 검색
- 반응형 편집 화면

완료 기준: 2주 동안 실제 메모와 할 일을 기록할 수 있고 저장 손실 없이 기존 Mano와
병행 사용한다.

### Phase 2 — 구조화된 데이터

- 표 기반 데이터 모음
- 속성: 텍스트, 숫자, 선택, 다중 선택, 날짜, 체크박스, 페이지 연결
- 필터, 정렬, 기본 테이블 뷰 저장
- 각 행을 페이지로 열어 추가 블록 작성

완료 기준: Daily/Monthly Todo와 간단한 목록을 전용 화면 없이 구성할 수 있다.

### Phase 3 — 기존 기능 연결

- Calendar, T1, 블로그 댓글, 자동화, 서비스 상태 연결 블록
- 페이지 템플릿과 자주 쓰는 대시보드
- 연결 데이터의 권한, 오류, 빈 상태와 새로고침 규칙 통일

완료 기준: 기존 기능의 핵심 확인·처리 흐름을 새 홈에서 수행하되 원본 전용 화면과
결과가 일치한다.

### Phase 4 — 사용자 구성 기능 완성

- Board, List, Calendar, Gallery와 Timeline 뷰
- 관계, 계산 속성, 그룹과 저장된 복합 필터
- 데이터 소스별 액션 버튼과 오류·재시도 상태
- 기존 기능을 재현하는 수정 가능한 선택형 템플릿

완료 기준: 사용자가 코드 수정 없이 기존 Mano의 각 전용 페이지를 새 페이지로 직접
구성하고 동일한 핵심 동작을 수행할 수 있다.

### Phase 5 — 기존 화면 제거

- 기능별 실제 사용량과 중복 유지 비용 검토
- 기능별 계약 테스트로 새 페이지와 기존 화면의 결과 일치 확인
- 명시적인 데이터 이관 도구, 백업과 롤백 절차 마련
- 기존 메뉴를 먼저 숨기고 관찰 기간 후 전용 라우트와 UI 코드 제거
- 수집기·scheduler·알림 API는 데이터 소스로 연결해 계속 유지

어떤 기존 기능도 비슷한 화면이 생겼다는 이유만으로 제거하지 않는다. 사용자가 직접 만든
페이지에서 데이터 조회뿐 아니라 생성·수정·완료·재시도 같은 동작까지 대체되어야 한다.

## 13. 대표 사용자 시나리오

1. 홈을 열어 오늘 페이지에 생각을 바로 적고 일부 줄을 Todo로 바꾼다.
2. 프로젝트 페이지 아래 회의 페이지를 만들고 관련 할 일과 일정을 한곳에 둔다.
3. 블로그 운영 페이지에서 오래된 미답글 묶음을 확인하고 완료 처리한다.
4. T1 페이지 블록에서 다음 경기와 라이브 상태를 확인하고 상세 화면으로 이동한다.
5. 운영 대시보드에서 서비스 장애와 실패한 자동화를 확인한다.

각 시나리오는 데스크톱과 모바일에서 핵심 작업을 완료할 수 있어야 한다.

## 14. 예외와 실패 처리

- 네트워크 단절: 편집 내용을 로컬에 보존하고 연결 복구 후 재시도한다.
- 저장 충돌: 서버 내용을 덮지 않고 양쪽 내용을 비교하거나 사본으로 보존한다.
- 잘못된 블록 JSON: 서버가 거절하고 마지막 정상 내용으로 화면을 유지한다.
- 연결 데이터 제공처 장애: 페이지 편집은 계속 가능하며 해당 블록만 오류 상태를 보인다.
- 페이지 삭제: 하위 페이지를 포함한 영향을 안내하고 휴지통에서 복구할 수 있게 한다.
- 대량 재정렬: 원자적으로 처리하고 일부만 이동된 상태를 남기지 않는다.
- 브라우저 종료: 미저장 표시와 마지막 전송을 시도하되 성공하지 않은 저장을 성공으로
  표시하지 않는다.

## 15. 보안과 운영

- 기존 Cloudflare Access와 Mano 단일 사용자 인증 경계를 유지한다.
- 렌더링 가능한 HTML을 그대로 저장·출력하지 않고 허용된 인라인 표현만 사용한다.
- URL, 첨부 파일과 연결 블록 입력을 서버에서 검증한다.
- 변경 이력과 백업에 개인 데이터가 포함됨을 전제로 접근 범위를 제한한다.
- DB migration은 기존 테이블을 변경하기보다 새 테이블 추가부터 시작한다.
- 배포 전 백업과 복구 절차를 확인하며 운영 migration은 별도 승인 후 실행한다.
- 자동 저장 오류율, API 지연, 충돌 건수와 최근 scheduler 상태를 관찰 가능하게 한다.

- 변경 이력 보존 기간과 사용자 복구 UI 범위

기존 기능이나 테이블을 제거하지 않는다.

## 20. 첫 구현 슬라이스

첫 구현은 화면보다 데이터 안전성 기반을 우선한다.

- 기존 `notes`, Todo, Calendar 테이블을 수정하지 않는 `workspace_pages`와
  `workspace_blocks` 테이블을 추가한다.
- 페이지와 블록은 soft delete, 정렬 위치, 정수 버전을 공통으로 가진다.
- MVP 블록 타입과 content 구조를 서버 도메인 계층에서 검증한다.
- 수정 요청은 현재 version이 일치할 때만 적용하는 낙관적 잠금을 사용한다.
- 부모 페이지와 부모 블록은 자기 자신을 가리킬 수 없도록 DB에서도 방어한다.

이 기반의 정상·경계·오류 테스트가 통과한 뒤 페이지 트리와 자동 저장 UI를 연결한다.

### 첫 편집 화면 API 계약

- `POST /pages`에 대응하는 서버 액션은 빈 최상위 페이지와 첫 Paragraph 블록을 하나의
  트랜잭션으로 만들고 `/pages/:id`로 이동한다.
- `PATCH /api/pages/:id`는 `{ title, version }`을 받아 version이 일치할 때만 저장한다.
- `PATCH /api/pages/:pageId/blocks/:blockId`는 `{ content, version }`을 받아 해당
  페이지에 속한 블록만 저장한다.
- 성공 응답은 증가한 `version`을 반환한다. 다른 탭에서 먼저 저장했으면 `409`, 잘못된
  입력은 `400`, 대상이 없으면 `404`를 반환한다.
- 클라이언트는 입력 후 600ms 동안 추가 입력이 없을 때 저장하고 `저장 중`, `저장됨`,
  `충돌`, `저장 실패`를 구분해 표시한다.

첫 화면에서는 최상위 페이지, 제목, Paragraph 블록과 새 Paragraph 추가만 제공한다.
페이지 중첩, 재정렬, 다른 블록 변환은 데이터 기반 위에 이어서 구현한다.

### 페이지 관리 슬라이스

- 페이지 목록은 부모·자식 계층으로 표시하며 고아 페이지도 잃지 않고 최상위에 둔다.
- 편집 중인 페이지 아래에 하위 페이지를 바로 생성할 수 있다.
- 즐겨찾기는 페이지 내용 version과 분리해 즉시 전환한다.
- 삭제는 `archived_at`을 기록하는 soft delete이며 하위 페이지도 함께 휴지통에 둔다.
- 복구할 때 부모가 아직 휴지통이면 해당 페이지를 최상위로 복구한다.
- 휴지통 비우기와 영구 삭제는 이번 범위에 포함하지 않는다.

### 블록 편집 슬라이스

- Paragraph, Heading, Bulleted list, Numbered list, Todo, Callout, Divider를 편집 화면에서
  서로 변환할 수 있다. Child page는 페이지 계층 액션으로만 만든다.
- `Enter`는 현재 블록 바로 다음에 Paragraph를 추가하고 새 블록으로 이동한다.
- Todo는 본문 자동 저장과 동일한 version 충돌 규칙으로 체크 상태를 저장한다.
- 블록 이동은 같은 페이지의 같은 부모 안에서만 위·아래 한 칸씩 수행한다.
- 삭제는 블록의 `archived_at`을 기록하며 페이지의 마지막 블록도 삭제할 수 있다.
- 블록 변환·이동·삭제 API는 URL의 page ID와 실제 block 소속을 함께 확인한다.

### 빠른 탐색 슬라이스

- Pages 검색은 페이지 제목과 보관되지 않은 텍스트 블록의 `text`를 함께 조회한다.
- 검색어는 앞뒤 공백을 제거하고 100자로 제한하며, 휴지통 페이지는 결과에서 제외한다.
- 검색하지 않을 때 최근에 연 페이지를 별도 영역에 최대 8개 표시한다.
- 빈 Paragraph에서 `/`를 입력하면 블록 종류를 고르는 메뉴를 연다.
- `/` 메뉴는 `Escape`로 닫고 선택 시 명령 문자 대신 선택한 블록으로 바꾼다.
